# Release v1.3.1

[![GitHub Downloads](https://img.shields.io/github/downloads/alexdelprete/ha-4noks-elios4you/v1.3.1/total?style=for-the-badge)](https://github.com/alexdelprete/ha-4noks-elios4you/releases/tag/v1.3.1)

**Release Date:** 2026-05-31
**Type:** Patch release — single options-flow bug fix reported during v1.3.0 testing.

---

## Overview

v1.3.1 fixes one user-facing bug discovered shortly after the v1.3.0 stable release: the
**Recovery Script** field in the Options flow couldn't be cleared. Submitting the form with
the field empty had no effect — the previously-saved script value stayed attached to the
config entry, kept appearing on form reopen, and continued to execute on connection failures.

If you weren't using a Recovery Script, or you want to keep the one you have, this release is
a no-op for you. If you've been trying (and failing) to remove a Recovery Script via the UI,
this release lets you do it.

---

## What's Changed

### 🐛 Bug Fix

- **Clearing the Recovery Script via the Options flow now works.** Open Options → clear the
  Recovery Script field → submit. Reopen Options: the field is empty. The cleared script no
  longer fires on connection failures.

### Root cause

The options-flow schema used:

```python
vol.Optional(
    CONF_RECOVERY_SCRIPT,
    default=recovery_script,   # ← bug
): EntitySelector(EntitySelectorConfig(domain="script")),
```

When the user cleared the EntitySelector and submitted, the Home Assistant frontend sent the
field as **absent** from the form data. Voluptuous's `default=` then substituted the
previously-saved value back in. So the cleared submission arrived at `async_step_init` already
carrying the old script value, which got saved straight back via
`async_create_entry(data=user_input)`.

### Fix

Switch to `description={"suggested_value": ...}`, which pre-fills the form for display but
does not resurrect a cleared value:

```python
vol.Optional(
    CONF_RECOVERY_SCRIPT,
    description={"suggested_value": recovery_script},
): EntitySelector(EntitySelectorConfig(domain="script")),
```

A missing key now flows through to the saved options. The coordinator already reads the value
with `config_entry.options.get(CONF_RECOVERY_SCRIPT, DEFAULT_RECOVERY_SCRIPT)` where the
default is `""`, and every consumer of `self._recovery_script` guards with a truthy check, so
no other code changes were needed.

### ✅ Tests

- Added a regression test that exercises the actual voluptuous schema, not the post-form
  handler. The bug lived in schema validation that runs **before** `async_step_init` is
  called — a naive test that calls `async_step_init({...})` directly with a hand-crafted
  dict bypasses the bug entirely. The new test pulls the schema out of
  `async_show_form`'s result and applies it to a synthetic "cleared" submission.

### ⚠️ Breaking Changes

**None.** Pure bug fix. Existing recovery scripts continue to work; only the inability to
clear them is gone. Config entries are unchanged.
