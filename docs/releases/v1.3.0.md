**Release Date:** 2026-05-31

**Type:** Minor release — official stable promotion of the ConnectionManager refactor that
resolves the recurring "device deafness" symptom. Fully backward compatible.

---

## Overview

`v1.3.0` is the stable promotion of the `1.3.0-beta.1` work. It re-architects the connection
layer into an explicit state machine (`ConnectionManager`), adds adaptive exponential backoff,
and exposes connection-health diagnostic sensors — directly targeting the long-standing issue
where the Elios4you device would periodically stop responding ("go deaf") and required a manual
WiFi reconnect to recover.

### Validated on a live device

The beta was run on a production device for several days before this promotion. Over a
representative ~8-hour window:

| Metric | Result |
|---|---|
| Silent timeouts (device went deaf) | **17 — all auto-recovered** |
| Command failures surfaced to entities | **0** |
| Device offline events | **0** |
| Connection reuse efficiency | **~99.96%** (2825 reuses / 2826 commands) |
| Manual "kick device off WiFi" workaround used | **0 times in 4+ days** |

The recovery is transparent: each silent timeout is detected, the socket is force-aborted with
a TCP RST, the connection is reopened, and the command is retried — all before any entity goes
stale.

## What's Changed

### 📊 Connection Diagnostics

- **12 diagnostic sensors** under the device's Diagnostic section. **Four are enabled by
  default** (up from two in beta.1) so connection health is visible out of the box:

  | Sensor | Default | Role |
  |---|---|---|
  | `Connection State` | ✅ | Current link state (`ready` / `connecting` / `backoff` / …) |
  | `Connection Consecutive Failures` | ✅ | Failure streak; non-zero means recovery is struggling |
  | `Connection Silent Timeouts` | ✅ | **Auto-recovered "device went deaf" events** |
  | `Connection Last Error` | ✅ | Last error message (empty when healthy) |
  | `Connection Backoff Remaining` | ⚪ | Seconds left in active backoff |
  | `Connection Reuse Hits` | ⚪ | Connection-pool reuse counter |
  | `Connection Connects Succeeded` | ⚪ | Successful TCP opens |
  | `Connection Connect Failures` | ⚪ | Failed TCP opens |
  | `Connection Commands Sent` | ⚪ | Total commands issued |
  | `Connection Commands Failed` | ⚪ | Commands that failed after all retries |
  | `Connection Commands Retried` | ⚪ | Commands that needed a retry |
  | `Connection Forced Aborts` | ⚪ | Error-path RST closes |

- **Why `Connection Silent Timeouts` is enabled by default:** auto-recovery resets
  `Connection Consecutive Failures` to `0` and keeps `Connection State` at `ready`, so a
  device that is still going deaf under the hood would otherwise be **invisible**. This counter
  is the only signal that surfaces it.
- **Downloadable diagnostics** (Settings → Devices → ⋮ → Download diagnostics) now include a
  `connection_manager` section with the full metrics snapshot.

### 🏗️ Architecture

- **New `connection_manager.py` module.** The connection lifecycle is an explicit state machine
  — `DISCONNECTED → CONNECTING → READY → BACKOFF`, terminal `CLOSED` on unload — that owns the
  single TCP/telnet session, serialises every command, and decides when to reconnect, retry,
  abort, or back off.
- **`api.py` thinned to a parser/orchestrator.** It formats the `@dat` / `@sta` / `@inf` /
  `@rel` commands and parses responses; all socket, retry, and backoff logic lives in the
  manager. Public API (`async_get_data`, `telnet_set_relay`, `close`, `data`, `name`, `host`)
  is unchanged.
- Removed the now-unused `check_port()` method and `as_diagnostics()` helper.

### 🚀 Reliability (device-deafness mitigations)

- **Reuse window raised to 90 s** (was 25 s) — the same TCP session persists across the poll
  cadence instead of opening a fresh socket every minute, drastically reducing pressure on the
  device's small socket table.
- **Retries dropped from 3 to 1** per command — worst-case connect-storm on a flaky cycle is
  now ~6 SYNs instead of ~12.
- **TCP RST on error close** (`transport.abort()`) instead of FIN — a failed command drops the
  socket with RST so the device frees its slot immediately rather than waiting out CLOSE_WAIT.
- **Bounded `wait_closed()`** — a misbehaving device can no longer hang the integration on close.
- **Exponential backoff** after 3 consecutive failures (5 s → 60 s, capped) — while in backoff
  the manager refuses to even attempt a new connection, giving the device room to recover.

### 🔧 Logging

- **Structured `(ConnMgr.*)` prefix** for every state transition, connect attempt, retry,
  close, and backoff event. To scope debug logging to just the manager:

  ```yaml
  logger:
    default: warning
    logs:
      custom_components.4noks_elios4you.connection_manager: debug
  ```

### 🧹 Code Quality

- Dropped every `# type: ignore` comment. `DataUpdateCoordinator[bool]` and
  `CoordinatorEntity[Elios4YouCoordinator]` are now properly parameterised, and the Unicode
  telnetlib3 variants are `cast()` at the assignment site.
- **Test coverage:** 99% overall, 211 tests passing.

### 📚 Documentation

- README rewritten: the architecture split, the `(ConnMgr.*)` log format, and the four
  default-enabled diagnostic sensors are documented.
- All pre-existing pymarkdown `MD032` violations across `CLAUDE.md`, `CHANGELOG.md`,
  `README.md`, and the full `docs/releases/` history are fixed — CI Lint is green.

### ⚠️ Breaking Changes

**None.** `api.py`'s public surface is unchanged. Existing config entries, sensors, the relay
switch, and automations keep working without modification. Migration from any prior version is
seamless.

## Upgrade & Rollback

**Upgrade:** HACS → Integrations → 4-noks Elios4you → Update to `1.3.0`. Restart Home Assistant.
The four default-enabled diagnostic sensors appear on the device page.

**Rollback:** downgrade to `1.2.0` via HACS if needed. Config entries are forward-compatible —
no migration loss.

## Watching Connection Health

After upgrading, the four default sensors tell the whole story at a glance:

- `Connection State` should sit at `ready` and **never** stay in `backoff`.
- `Connection Consecutive Failures` should stay at `0`.
- `Connection Silent Timeouts` may tick up slowly (each one was auto-recovered); rapid growth
  means the device is dropping commands faster than before.
- `Connection Last Error` should be empty.

To get a push notification on deaf events, add an automation on the **rate of change** of
`Connection Silent Timeouts` — the counter is monotonic, so trigger on an increase over a
time window rather than on an absolute value.
